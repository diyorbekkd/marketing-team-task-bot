No production data or settings were changed. The browser had no authenticated app session, so task creation, approval, and checklist latency could not be measured end to end.

## Findings, in order

### P0 — production and Preview are far apart

The live deployment and database predate 17 migrations and the recent login, AI, planning, workflow, video, notification, and template work. Production already has 198 real tasks. A green Preview build and migration smoke on a 21-task staging database do not prove that the live upgrade is safe. Before release, run all pending migrations against a production-shaped copy, check preserved task/event counts and permissions, then do signed-in Head, employee, operator, bot, and cron acceptance on Preview. Make a backup and a rollback plan for the production rollout.

### P1 — task detail and mutation paths have excessive round trips

`MarketingService.getTaskDetails` first reads the task, then issues up to ten related reads (`src/application/marketing-service.ts:813`). The recurring-definition read fetches the same task again (`src/server/repositories/supabase-marketing-repository.ts:1019`), and template instances need a second serial lookup (`:615`). Every request also fetches the actor (`src/server/auth/request-actor.ts:10`). A task action updates the UI, then refetches the whole detail and Home/Tasks lists (`src/components/mini-app/MiniApp.tsx:2065`). The action route defers Telegram delivery but still waits for recipient lookup and outbox enqueue before returning (`src/application/marketing-service.ts:1062,1523`). Checkpoint actions refetch both My Day and task detail after applying the returned checkpoint; a checkpoint toggle itself waits for POST before changing the checkbox (`src/components/mini-app/TaskPlanningPanel.tsx:83`). SQL is quick in the staging sample, so request count and network/cold-start overhead are stronger latency hypotheses than missing indexes. Instrument API spans and client action-to-visible-change first, then reduce detail reads, remove the duplicate task lookup, make checkpoint toggles optimistic, and refresh only affected data.

### P1 — a committed task can lose its notification; a retry can duplicate it

Browser task creation commits the task before queueing assignment/creator/topic messages (`src/application/marketing-service.ts:475`). If enqueue fails, the code logs a failure and returns the task, but there is no outbox row to retry (`:489`). Browser action notifications have a similar caught-and-logged enqueue failure path (`:1523`). The browser create RPCs pass no idempotency key (`src/server/repositories/supabase-marketing-repository.ts:633`; `supabase/migrations/20261119075915_relative_checkpoint_task_templates.sql:97`), so a timed-out response followed by a user retry can create another task. Insert the durable outbox entry in the same transaction as the state change where feasible; give browser create requests a stable client-generated operation ID and enforce uniqueness in the database. Keep the current UI warning for any delivery failure.

### P1 — event-date changes do not notify the assignee

`rebaseTaskTemplateEvent` updates a template task's deadline/checkpoint dates and writes audit events (`supabase/migrations/20261119075915_relative_checkpoint_task_templates.sql:118`), but its service method only returns fresh details (`src/application/marketing-service.ts:1189`). The responsible employee will not receive a bot notification when the event moves. Queue one concise schedule-change message for affected people, with the old and new dates, after the database change; make it durable/idempotent.

### P2 — templates can schedule work beyond the task deadline

The template schema validates offsets and times separately (`src/domain/task-template.ts:3`) but does not compare the last checkpoint against the task deadline. A manual deadline override can also move the deadline earlier than checkpoints. The task can then be overdue before its planned work is due. Show a warning and require an intentional override, or adjust the deadline proposal to cover the latest checkpoint. There are currently zero saved staging templates, so the first real Webinar template still needs a Head click-through.

### P2 — reports and Home read growing full collections

Reports load every task and task event and recalculate metrics in memory (`src/application/marketing-service.ts:1439`; `src/server/repositories/supabase-marketing-repository.ts:713,809`). Home loads every open task for the relevant scope (`:728`). This is acceptable at 21 staging tasks and still modest at 198 production tasks, but will grow linearly and add pages of Data API calls. Add bounded date/status queries or a server-side summary before the dataset becomes large; retain the current actor-scoped report response.

### P2 — release acceptance and observability have gaps

Unit/API tests cover 292 cases, but there is no automated signed-in browser journey for Head and ordinary employee, and no recorded action p50/p95 or mobile web vitals. The public login page loaded, but the audit browser had no app session. Measure at least opening a task, checklist toggle, create, approval, and report load from actual Telegram/mobile and desktop sessions. Include video scheduling, template creation/rebase, and one AI action proposal/confirmation in acceptance. Log request IDs and timing breakdowns without secrets. Verify notification outbox and cron delivery after release.

### P2 — missing operational content and small UX failure

`src/server/assistant/TEAM_SOP.md` still says no Head-approved SOP exists. AI can give generic task guidance but cannot reliably answer team-specific rules; the discussed Notion synchronization is not in place. For task actions it sees at most 20 soonest open tasks and 20 recently created open tasks (`src/application/assistant-service.ts:61`), so an older task may be impossible to select by name; add a scoped search tool/query before promising arbitrary task edits. Preview's video-topic relay is disabled until a real group/topic is chosen and has never sent a live group message. The Quick Add template fetch ignores API errors and can silently show an empty picker (`src/components/mini-app/MiniApp.tsx:3247`). Surface a retry/error state.

## Performance order of work

1. Add action-to-visible-change timings in Preview, with API breakdown and p50/p95; obtain one signed-in mobile and desktop sample.
2. Consolidate the task-detail reads and remove redundant refreshes after mutations; compare before/after timings.
3. Add browser create idempotency and atomic notification outbox enqueue; test timeout/retry and enqueue failure.
4. Bound report/Home queries as task/event volume increases. Add only indexes justified by slow-query evidence; the staging advisor's unindexed-FK and unused-index notices are informational at this size.
5. Run the production-shaped migration rehearsal and full role/bot acceptance before deploying the new branch.

## Existing strengths

Permission checks are server-side, task/event writes use database RPCs, task lists are paginated and default to newest first, and posting-checklist toggles update optimistically. Supabase browser roles are intentionally denied table access despite informational RLS-without-policy advisor notices. Vercel functions and both Supabase projects are in Mumbai, so there is no obvious Vercel-to-database region mismatch.
