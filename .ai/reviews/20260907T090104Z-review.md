## Medium

**M1 — `dispatchWorkflowNotification` issues an extra `listUsers()` query after every committed mutation (marketing-service.ts:308)**

After the database transaction for the state change has already committed, `dispatchWorkflowNotification` calls `this.repository.listUsers()` to resolve recipient IDs to full `User` objects. A transient failure on this secondary query silently suppresses all workflow notifications for that event (logged as `RECIPIENT_LOOKUP_FAILED`; no caller sees an error). The design choice to never propagate notification failures is correct for preserving workflow state, but the dependency on a post-commit DB call for every workflow event creates an independent failure mode with no retry path. At N=5 this is low operational risk, but it is a reliability concern per the severity rubric. Calling `listUsers()` is also a full-table scan on every callback. A targeted `getUserById` per recipient would avoid both issues.

## Low

**L1 — `resolutionNote` is not included in the `DEADLINE_CHANGE_REJECTED` notification (telegram-notification-dispatcher.ts:91–95)**

When a creator or Head rejects a deadline request and supplies a `resolutionNote`, the rejection notification sent to the assignee omits that note. The `workflowMessage` case for `DEADLINE_CHANGE_REJECTED` only shows the task title. The `resolutionNote` is available on the `resolvedRequest` object already passed to `dispatchWorkflowNotification` (marketing-service.ts:294–296). This is a UX gap but not a data-loss issue (the note is in the audit record).

**L2 — Redundant duplicate IDs passed to `dispatchWorkflowNotification` in `resolveDeadlineChangeRequest` (marketing-service.ts:290–298)**

`[request.requestedBy, task.assigneeId]` is always the same user ID, because only the assignee may create a deadline request. The `new Set()` deduplication at line 310 handles it, but the intent at the call site would be clearer with a single `[task.assigneeId]`.

**L3 — No notification dispatched for `RESUME` from `BLOCKED` state**

`TASK_BLOCKED` is now notified (creator + Head), but `RESUME` (which unblocks) triggers no notification. The product spec says "Creator and Head will later be notified" for blocking/unblocking; "later" is ambiguous about unblocking. The sprint does not explicitly require it, so this is a gap to track rather than a blocking defect.

**L4 — Head-is-creator deduplication path has no direct test**

When the Head is also the task creator and `includeHeads = true`, the same user appears in both `directRecipients` and `heads`, so `recipients` contains them twice. The dispatcher's `recipientKey` dedup (`telegram:ID`) handles it correctly, and a dispatcher-level test exists (`deduplicates creator and Head by Telegram user ID for a deadline request`). However, there is no service-level test that exercises this combined path end-to-end.
