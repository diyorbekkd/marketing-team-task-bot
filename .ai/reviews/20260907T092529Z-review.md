## High

None. Authorization is correctly maintained across both new callback paths:

- **Deadline callbacks** (`deadline:UUID:APPROVE|REJECT`) resolve through `service.resolveDeadlineChangeRequest`, which calls `canApproveDeadlineRequest` (creator or Head only) and `CONFLICT`-guards already-resolved requests (`marketing-service.ts:281`). This satisfies the "first resolution wins" invariant from the product spec.
- **`REQUEST_REVISION` callback** routes through `performTaskAction` which enforces the `reviewerAction` guard (`isCreator || isHead`) at `marketing-service.ts:197`. `reason` is optional per `TaskActionInputSchema` and the product spec ("optional explanatory text").
- Positional task creation still requires an active onboarded sender (`requireActorByTelegramId`) and active onboarded assignee (`findActiveUserByUsername`) before any persistence, the same contract as the labeled format.
- Notification failures are fully decoupled from committed workflow state — the mutation completes and is logged regardless of delivery outcome.

## Medium

**`looksLikePositionalTask` triggers on date line alone, without @username on line 2 — bot sends unsolicited error messages to the group**

`task-shorthand.ts:47`:
```ts
return hasDeadlineShape || (hasAssigneeShape && hasDeadlineHint);
```

`hasDeadlineShape` is `true` whenever line 3 (third meaningful line) exactly matches `DD.MM.YYYY HH:mm` or `DD.MM HH:mm`, regardless of whether line 2 is `@username`. When this fires, `parseGroupTaskMessage` calls `parsePositionalTask`, which throws `TaskShorthandError("Line 2 must be exactly @username.")`.

In `handler.ts:160-170`, the handler then:
1. Performs a database call (`requireActorByTelegramId`)
2. Logs a warn
3. Re-throws — causing the outer catch to send `taskFormatError(...)` back to the marketing group

Any three-line group message where the third meaningful line happens to look like a date/time (meeting schedules, calendar shares, delivery deadlines shared in-chat) will cause the bot to respond with an error message. `PRODUCT.md` specifies: *"positional input is considered only in the configured marketing group when its **assignee/deadline** lines have the task shape"* — both lines, not the deadline line alone.

The "silently ignores ordinary conversation" handler test (`telegram-handler.test.ts:1281`) and the shorthand unit test (`task-shorthand.test.ts:997`) only cover cases where `parseGroupTaskMessage` returns `null`. Neither covers the false-positive path where `looksLikePositionalTask` returns `true` but line 2 is not `@username`.

## Low

**`dispatchWorkflowNotification` inconsistently deduplicates between direct recipients and heads**

`marketing-service.ts:310,331`:
```ts
const recipientIds = [...new Set(directRecipientIds)]; // dedup by ID
// ...
const recipients = [...directRecipients, ...heads];    // heads not deduped against directRecipients
```

When the task creator is also the Head (a documented product scenario), the Head user appears twice in the `recipients` array passed to the dispatcher. `TelegramNotificationDispatcher` correctly deduplicates by `telegramUserId` (`recipientKey`), so no double message is sent, but the service delegates what it could resolve itself. This is a clarity/consistency note, not a functional bug.

**No test covering the `looksLikePositionalTask` false-positive path**

The existing `task-shorthand.test.ts` "silently ignores" cases (`"Bugun yig'ilish bor\nHamma qatnashsin\nSoat oltida"`) avoid the bug because "Soat oltida" doesn't match `hasDeadlineShape`. A case like `"Yig'ilish\nHamma kelsin\n09.09.2026 14:00"` would expose the false positive and is not covered.

## Required fixes before merge

None blocking — no Critical or High findings. The MEDIUM issue imposes real UX risk but no security, authorization, or data integrity violation. Risk is mitigated by the fact that the group is a small closed team and date/time in position 3 is uncommon in typical marketing conversation; however, the spec deviation is clear.

## Optional improvements

1. **Fix `looksLikePositionalTask` to require both lines** — change the predicate to require `hasAssigneeShape && (hasDeadlineShape || hasDeadlineHint)`. This brings the classifier in line with the product spec ("when its assignee/deadline lines have the task shape") and eliminates the false-positive bot responses for messages with dates in the third line but no @username in the second.

2. **Add a test for the false-positive path** — cover `parseGroupTaskMessage` (and the handler) with a three-line message where line 3 is a valid date but line 2 is plain text; assert the classifier returns `null` (after the above fix) and no bot message is sent.

3. **Pre-deduplicate heads against direct recipients in `dispatchWorkflowNotification`** — build a single deduplicated recipient set by user ID before calling the dispatcher, removing the implicit dependency on dispatcher-level deduplication for correctness.
