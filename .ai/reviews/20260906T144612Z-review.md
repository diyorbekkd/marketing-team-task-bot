## Medium

### M1. `src/server/config.ts` lacks `import "server-only"` guard

**Confirmed risk.** This module exports functions that read `SUPABASE_SERVICE_ROLE_KEY`, `TELEGRAM_BOT_TOKEN`, and `TELEGRAM_WEBHOOK_SECRET` from `process.env`. Both `src/server/db/supabase.ts:1` and `src/telegram/client.ts:1` correctly include `import "server-only"`, but the config module itself — which is the primary secret accessor — does not.

If a future client component mistakenly imports `@/server/config`, Next.js would not fail the build. While `process.env` values without `NEXT_PUBLIC_` prefix would be `undefined` at build time (preventing actual leakage), the code path would still ship to the client bundle and the build would not produce a clear error.

Adding `server-only` to `config.ts` would break `tests/config.test.ts` (Vitest is not a React Server Component context), but that is resolvable with a Vitest module alias or mock for `server-only`.

**File:** `src/server/config.ts:1` (missing import)
**Type:** Defense-in-depth gap for secret-handling module.

### M2. Unhandled `sendTelegramMessage` failure surfaces 500 to Telegram

**Confirmed defect.** In `src/app/api/telegram/webhook/route.ts:37`, if `sendTelegramMessage` throws (network timeout from the 8-second `AbortSignal`, invalid bot token, Telegram API outage), the error propagates to Next.js's default handler, resulting in a 500 response. Telegram will retry the update, potentially causing repeated failures.

For Sprint 0 (only `/start` replies), the blast radius is very small, but the route should catch the error, log it, and still return `{ ok: true }` — the webhook acknowledgment and the reply delivery are separate concerns. Telegram's retry mechanism is designed for delivery to the bot, not for the bot's outbound calls.

**File:** `src/app/api/telegram/webhook/route.ts:35-40`

## Low

### L1. No test for an unrelated user being denied task access

`tests/permissions.test.ts` exercises assignee, creator, and Head actors thoroughly. It does not test a fourth actor who is none of these (an arbitrary team member unrelated to the task). While the code path is implicitly covered (all three `is*` checks return `false` → `canEditTask` returns `false`), an explicit test would strengthen the permission boundary.

**File:** `tests/permissions.test.ts`

### L2. `getTelegramConfig()` parsed twice per webhook request

The webhook route handler calls `getTelegramConfig()` at line 9, and then `sendTelegramMessage` (line 37) internally calls `getTelegramConfig()` again at `src/telegram/client.ts:4`. Parsing cost is negligible for Sprint 0 volume, but the config could be threaded through or the Telegram config cached at module scope.

**File:** `src/app/api/telegram/webhook/route.ts:9` and `src/telegram/client.ts:4`

### L3. Bot token in fetch URL could appear in runtime error traces

`src/telegram/client.ts:13` constructs `https://api.telegram.org/bot${botToken}/sendMessage`. While the custom error messages at lines 23-24 do not include the token, some Node.js runtime error conditions (especially `TypeError` from malformed URLs) could include the full URL in stack traces or diagnostic logs. Standard practice for Telegram bots, but worth noting for production log hygiene.

**File:** `src/telegram/client.ts:13`

## Required fixes before merge

1. **M2**: Wrap the `sendTelegramMessage` call in the webhook route in a try/catch. Log the failure and return `{ ok: true }` regardless, so Telegram does not retry the update due to a failed outbound reply. This separates webhook acknowledgment from reply delivery.

## Optional improvements

1. **M1**: Add `import "server-only"` to `src/server/config.ts` and configure the Vitest environment to mock/alias that import. This provides build-time protection against accidental client-side import of secret-handling code.

2. **L1**: Add a test case for a user who is neither assignee, creator, nor Head being denied all task edit permissions.

3. **L2/L3**: Consider passing the already-parsed config to `sendTelegramMessage` rather than having it re-read environment variables. This avoids redundant parsing and gives the caller control over how the token is handled.

4. **Schema comment**: The `deadline_change_requests` and `reassign_requests` tables each have a `CHECK (current_deadline <> requested_deadline)` / `CHECK (current_assignee_id <> requested_assignee_id)` constraint, which is good. A database-level FK or trigger to verify that `current_deadline` / `current_assignee_id` matches the actual task row at insert time would further strengthen integrity. This is appropriately deferred to the Sprint 4 RPC functions per the architecture doc.
